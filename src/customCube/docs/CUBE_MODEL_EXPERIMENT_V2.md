# Cube Model Experiment Sprint v2 — 신규 후보 3종 (Facelet-Cycle / Sparse-Touched / Bitboard)

## 배경

"다다익선"이라는 사용자 지시에 따라 제안했던 3개 신규 후보(A. Facelet-Cycle,
B. Bitboard, C. Sparse-Touched)를, 앞서 검증했던 3개 모델(Delta-Log /
Discrete-Twist / Slot-Cycle)과 동일한 절차 — 정합성 벤치마크 + 성능
벤치마크, `customCubeExperiments/` 안에서만 작업, 프로덕션 파일 변경
0건 — 로 실제로 구현하고 검증했다.

## 모델 소개

### A. Facelet-Cycle

Slot-Cycle은 "피스"(코너/엣지/센터 하나) 단위로 위치+방향을 추적한다.
하지만 `FaceletSnapshot.ts`(정합성 판정 기준) 자체는 피스 그룹핑을 전혀
요구하지 않고 스티커 하나하나의 (위치, 방향, 색) 만 본다. 그래서
Facelet-Cycle은 "피스"라는 개념 자체를 버리고, 스티커 하나를 고정 슬롯
하나로 취급한다. 위치와 방향이 항상 같이 회전하므로(같은 피스의 같은
모서리에 딱 붙어 있으므로), 슬롯 자체가 이미 "방향"까지 포함하고
있어서 — Slot-Cycle이 쓰던 회전군 인덱스 자체가 필요 없어진다. 대신
슬롯 개수가 피스보다 많다(코너 1개=슬롯 3개).

### C. Sparse-Touched

프로덕션의 `cloneCubies`는 몇 턴을 돌렸든 상관없이 항상 전체 피스를
순회하며 새 객체를 만든다. 5x5(98피스)에서 살짝만 스크램블한 경우, 대부분의
피스는 여전히 완전히 solved 상태인데도 매번 새 Vector3/Quaternion을
할당한다. Sparse-Touched는 실제로 한 번이라도 움직인 피스만 `Map`에
기록하고, `toCubies()`에서 Map에 없는(=한 번도 안 움직인) 피스는 캐시된
solved 객체를 참조로 그대로 반환한다(클론 없음). 단, `toCubies()`는
여전히 전체 피스 수만큼 `Map.get()` 조회는 수행한다 — 할당만 건너뛸 뿐
순회 자체를 건너뛰진 않는다는 점은 설계상의 한계로, 실측 결과에도
그대로 드러난다(아래 참고).

### B. Bitboard — 범위 정정 포함

원래 제안 단계에서 "3x3 전용"이라고 설명했는데, 실제 구현하면서 그 이유가
당초 생각과 달랐다는 점을 정정한다.

- **정정 전 설명**: "코너/엣지 좌표 분리가 3x3 전용 개념이라서."
- **실제 구현이 3x3 전용인 진짜 이유**: 코너 8개 + 엣지 12개 + 센터
  6개라는 분할 자체가 3x3x3의 고정된 구조적 사실이다(2x2는 엣지/센터가
  아예 없고, 4x4/5x5는 엣지가 윙 형태로 여러 서브타입에, 센터도 다수의
  면 조각으로 나뉘어 이 분할과 1:1 대응하지 않는다).
- **정직하게 밝히는 스코프 축소**: 교과서적인 "최소 좌표계"(코너 방향은
  Z3, 엣지 방향은 Z2로 압축)까지는 가지 않았다. 이미 검증된
  `RotationGroup.ts`의 24개 회전군 인덱스를 코너/엣지/센터 모두 동일하게
  재사용하고, 그것을 3그룹으로 나눠 정수 몇 개에 비트 패킹만 했다. 즉
  이번에 실제로 검증한 가설은 "최소 좌표계"가 아니라 좁혀서 "배열 인덱싱
  대신 비트 시프트/마스크로 접근하는 정수 패킹 저장소가 Slot-Cycle과
  같은 순열 사이클 기법 위에서 이득이 있는가" 하나다.

상태: `cornerPerm`(8×3bit), `cornerOri`(8×5bit), `edgePerm`(12×4bit),
`edgeOri`(12×5bit), `centerPerm`(6×3bit), `centerOri`(6×5bit) — 정수
9개. 슬라이스 턴(레이어 0)이 센터 4개를 서로 맞바꾼다는 사실을 직접
좌표 계산으로 재확인하고서(직관과 달리 센터도 고정이 아니다) 센터까지
추적 대상에 포함시켰다.

## 검증 방법

`ExperimentHarness.ts`의 `runCorrectnessCheck`/`runPerformanceBenchmark`를
그대로 재사용(`runCubeModelExtendedSprintV1.ts`).

- **정합성**: gridSize 2~5, 각 40시퀀스×80턴 (Bitboard는 3x3만, 구조상
  다른 크기를 지원하지 않으므로).
- **성능(표준)**: gridSize 3/5, 4,000턴, "매 턴 즉시 해석" 시나리오.
- **성능(얕은 스크램블, Sparse-Touched 전용 가설 검증)**: 5x5에서
  스크램블 깊이를 1/2/3/5/8/15턴으로 바꿔가며, 스크램블 후 새 턴 없이
  `toCubies()`만 8,000회 반복 호출 — "카메라만 돌리고 새 턴은 없는" 실제
  렌더링 패턴과 더 가깝다. 표준 4,000턴 벤치마크로는 대부분의 피스가
  금방 다 "손댄" 상태가 돼버려서 이 모델의 실제 가설(손댄 피스 수에
  비례)을 공정하게 볼 수 없기 때문에 별도로 추가했다.

측정 방법론 관련 투명성 노트: 드라이버 초안에서는 STEP2를 두 블록(첫
블록에서 gridSize 3/5, 두 번째 블록에서 Bitboard용 gridSize 3만 별도로)
으로 나눠 실행했는데, 같은 프로세스 안에서 두 번째 블록의 Ground
Truth/Slot-Cycle 수치가 첫 블록과 완전히 다르게 나오는 현상을 재현
확인했다(두 차례 독립 실행 모두에서 재현 — 앞 블록에서 대량으로 만든
정합성 검증용 시퀀스 배열의 GC 부담으로 추정). 이건 진짜 성능 차이가
아니라 측정 아티팩트라고 판단해, 같은 gridSize를 필요로 하는 모델은
전부 한 블록 안에서 한 번에 측정하도록 드라이버를 고쳐서 재실행했다 —
아래 수치는 그 수정된 드라이버의 결과다.

## 결과

### STEP1 — 정합성 (facelet-map 비교)

| 모델 | 2x2 | 3x3 | 4x4 | 5x5 |
|---|---|---|---|---|
| Facelet-Cycle | 40/40 | 40/40 | 40/40 | 40/40 |
| Sparse-Touched | 40/40 | 40/40 | 40/40 | 40/40 |
| Bitboard | — | 40/40 | — | — |

셋 다 정합성은 완전히 통과했다.

### STEP2 — 성능 (표준: 매 턴 즉시 해석, 4,000턴)

| 모델 | 3x3 | 5x5 |
|---|---|---|
| 프로덕션 (Ground Truth) | 22.1ms | 45.0ms |
| Slot-Cycle (기존 1위) | 13.0ms | 28.9ms |
| **Facelet-Cycle** | **14.5ms** | **30.7ms** |
| **Sparse-Touched** | **19.5ms** | **118.3ms** |
| **Bitboard** | **24.6ms** | — (3x3 전용) |

- **Facelet-Cycle**: 프로덕션보다 3x3에서 1.52배, 5x5에서 1.47배
  빠르다. Slot-Cycle에는 살짝(3x3에서 12%, 5x5에서 6%) 못 미치지만,
  스티커 단위라 슬롯 수가 더 많은데도(코너 1개=슬롯 3개) 이 정도
  차이밖에 안 나는 건 방향 추적(회전군 인덱스) 자체를 없앤 효과로
  보인다.
- **Sparse-Touched**: 3x3에서는 그나마 프로덕션(22.1ms)보다 빠르지만
  (19.5ms), 5x5에서는 오히려 프로덕션(45.0ms)보다 크게 느리다
  (118.3ms). 이건 설계 노트에서 이미 경고한 대로다 — 4,000턴을 다
  돌리면 98피스 대부분이 "손댄" 상태가 돼버려 Map 오버헤드만 남고 클론
  절약 효과는 사라진다. **표준 벤치마크만 보면 이 모델은 프로덕션보다
  못한 실패작이다.**
- **Bitboard**: 3x3에서 프로덕션(22.1ms)보다도 느리다(24.6ms), 물론
  Slot-Cycle(13.0ms)보다는 훨씬 느리다. 정수 패킹/언패킹 비용(매 턴, 매
  `toCubies()` 호출마다 배열 unpack → 셔플 → repack)이 배열 인덱싱보다
  비싸다는 뜻으로, "비트 패킹이 항상 빠르다"는 통념과 반대되는 정직한
  실측 결과다.

### STEP3 — 얕은 스크램블 해석 비용 (Sparse-Touched 가설 전용, 5x5, 8,000회 해석)

| 스크램블 깊이 | 프로덕션 | Slot-Cycle | Sparse-Touched |
|---|---|---|---|
| 1턴 | 51.7ms | 57.9ms | **29.2ms** |
| 2턴 | 47.3ms | 46.0ms | **26.2ms** |
| 3턴 | 43.9ms | 46.1ms | **30.8ms** |
| 5턴 | 44.9ms | 45.8ms | 41.2ms |
| 8턴 | 46.9ms | 47.4ms | 40.7ms |
| 15턴 | 46.2ms | 60.9ms | 45.9ms |

**Sparse-Touched의 가설은 좁은 범위에서는 실제로 맞다.** 스크램블이
1~3턴처럼 정말 얕을 때는 프로덕션/Slot-Cycle 대비 1.4~1.9배 빠르다
(98피스 중 극소수만 "손댄" 상태라서 대부분의 `toCubies()` 호출이 클론
없이 참조만 반환됨). 하지만 5턴을 넘어가면서 이득이 빠르게 줄고,
8~15턴 근처에서는 사실상 차이가 사라진다 — 한 턴이 5x5 한 레이어에서
건드리는 피스 수가 적지 않아서, 몇 번만 돌려도 "손댄" 피스 비율이
금방 올라가기 때문으로 보인다.

## 종합 평가

| 모델 | 정합성 | 성능 결론 |
|---|---|---|
| Facelet-Cycle | 100% | **일관된 승리** — 전 크기에서 프로덕션보다 1.4~1.5배 빠름, Slot-Cycle에 근접 |
| Sparse-Touched | 100% | **조건부** — 진짜 얕은 스크램블(1~3턴)에서만 우위, 그 외(특히 표준 4,000턴 포화 시나리오)에서는 프로덕션보다도 느림 |
| Bitboard | 100% | **실패** — 3x3 전 구간에서 프로덕션보다도 느림, 패킹/언패킹 비용이 저장 압축 이득을 상쇄 |

Facelet-Cycle은 기존 Slot-Cycle("CUBIXX 모델")에 필적하는 신규 승자
후보다. Sparse-Touched는 범용 대체재는 아니지만, "몇 수만 돌리고 다시
카메라만 조작하는" 특정 사용 패턴에서는 의미가 있다는 게 실측으로
확인됐다. Bitboard는 이번 구현 방식으로는 이점이 없다는 정직한
결론이다 — 셋 다 "다다익선"이라는 지시에 따라 실험해본 결과이며, 모든
후보가 승리할 필요는 없다.

프로덕션(`cubeState.ts`/`CustomCubeScene.ts`) 통합 여부는 이번 5개
모델(Delta-Log, Discrete-Twist, Slot-Cycle, Slot-Cycle+Log,
Facelet-Cycle) 전부에 대해 여전히 별도 결정 사항이며, 이번 Sprint에서도
프로덕션 코드는 전혀 건드리지 않았다.
