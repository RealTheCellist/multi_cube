# Gesture Axis Mapping Validation v4 — Margin-Scaled Confidence Gate

## 배경

사용자가 큐브 모델 교체보다 스와이프 방향 오인식("좌측/우측/상측 등 면과
면이 만나는 부분에서 다른 방향으로 오동작") 자체를 고치는 게 우선이라고
판단해, 모델 연구는 보류하고 이 문제에 다시 집중했다.

기존에 이미 3가지 방향이 시도됐고 전부 뚜렷한 개선을 못 만들었다:

| 시도 | 결과 |
|---|---|
| 신뢰도 게이트(V3, 고정 +20px) | 방향성 있는 개선(−1~−6%p)이나 N=50 표준오차 내, 마진<0.05는 못 고침 |
| 카메라 각도 추가 조정(Yaw −7°) | Top face는 개선, **Right face는 악화**(38%/44%→46%/50%) — 한 카메라로 여러 면을 동시에 만족 불가 |
| 다중 샘플 평균(PCA) | 헤드리스 시뮬레이션에서 **오히려 악화** — 판정 윈도우(8~28px)가 너무 짧아 샘플 수 자체가 부족 |

이번엔 네 번째 방향 — **신뢰도 게이트를 이진(고정 +20px)에서 마진에 따라
연속적으로 스케일링**하는 방식을 검증했다.

## 아이디어

기존 V3 게이트는 마진이 `LOW_CONFIDENCE_MARGIN`(0.15) 미만이면 마진이
0.14든 0.001이든 똑같이 +20px만 더 기다린다. 하지만 마진이 0에 가까울수록
(두 후보 탄젠트가 거의 평행) 손 떨림을 극복하려면 훨씬 더 긴 이동 거리가
필요하다 — 반대로 마진이 임계값에 가까운 경우는 원래도 거의 충분했다.
그래서 대기 거리를 마진에 반비례하는 연속 함수로 바꿨다:

```ts
const LOW_CONFIDENCE_MAX_EXTRA_PX = 80;
function lowConfidenceExtraPx(margin: number): number {
  return LOW_CONFIDENCE_MAX_EXTRA_PX * (1 - margin / LOW_CONFIDENCE_MARGIN);
}
```

마진이 `LOW_CONFIDENCE_MARGIN`에 가까울수록 추가 대기가 0에 가깝고(기존
동작과 동일), 마진이 0에 가까울수록 최대 80px까지 기다린다. 기존
20px보다 항상 크거나 같으므로(마진이 아주 낮지 않은 한) 기존 동작을
"덜 기다리게" 퇴화시키지 않는다.

## 검증 STEP1 — 헤드리스 시뮬레이션

`customSwipeControls.ts`의 `worldToScreen`/`screenTangent`/`axisAlignment`
수식과 실제 카메라 파라미터를 그대로 복제한 독립 스크립트로, V3와 같은
손떨림 모델(매 스텝 독립 노이즈, 진폭 4px)을 재현해 기존(고정 +20px) vs
신규(최대 +80px 연속 스케일링)를 같은 샘플 경로로 페어 비교했다(N=150/방향).

| 지점 | 기존(고정 +20px) | 신규(연속 스케일링) |
|---|---|---|
| Right face 최악(마진 0.003) | 0.7% / 4.0% 오인식 | **0.0% / 0.0%** |
| Top face 최악(마진 0.000, 완전 동률) | 44.0% / 50.7% 오인식 | **35.3% / 34.7%** |
| Front face(회귀 검사) | 1.3% / 6.7% | 1.3% / 6.7% (완전 동일) |

- 마진이 사실상 0인 Right face 지점은 사실상 해결됐다(0%).
- 마진이 **정확히 0**(두 탄젠트가 화면상 완전히 평행)인 Top face 지점은
  어떤 알고리즘으로도 이론상 50/50을 벗어날 수 없는 진짜 기하학적 한계지만,
  그래도 기존보다 9~16%p 낮아졌다.
- Front face는 게이트가 아예 발동하지 않는 마진 구간이라(항상 ≥0.3)
  완전히 동일한 결과 — 회귀 0%.

## 검증 STEP2 — 실제 코드 통합/기능 검증 (Playwright, 실제 dev 빌드)

시뮬레이션은 수식을 복제한 것이지 실제 코드를 실행한 게 아니므로, 실제
빌드에서 통합 오류(오타, 잘못된 변수 참조 등)가 없는지 별도로 확인했다.

- `npx tsc -b && npx vite build` — 정상 빌드 확인.
- 실제 dev 서버에 Playwright로 접속, 3x3 큐브를 선택한 뒤 앞면 수평/수직
  스와이프 2회 + 상단-우측 경계 부근(오블리크 각) 스와이프 2회를 실행:
  이동수 카운터가 0→1→2→3→4로 정확히 매 스와이프마다 1씩 증가 — 크래시,
  멈춤, 무반응 없이 정상 동작 확인.
- 콘솔 에러 0건(페이지 로드 시점부터 이미 존재하던 Google Fonts CDN 연결
  실패 1건은 샌드박스 네트워크 제약으로 인한 것으로, 상호작용 전부터
  존재하며 이번 변경과 무관함을 별도 확인).

**정직하게 밝히는 한계**: 이번 STEP2는 기능적 회귀 검사(정상 동작 확인)
이지 V3처럼 실제 브라우저에서 N=100 손떨림 기반 통계 재검증은 아니다.
STEP1의 통계적 근거는 실제 프로덕션 수식을 그대로 복제한 헤드리스
시뮬레이션에 기반한다. 실제 기기에서 체감 개선을 사용자가 직접 확인하는
것을 다음 단계로 남긴다.

## 판정

| 기준 | 결과 |
|---|---|
| Front face 회귀 없음 | **통과** — 시뮬레이션상 완전 동일(1.3%/6.7%), 실제 빌드 기능 검증도 통과 |
| 문제 지점 개선 | **통과** — Right face 사실상 해결(0%), Top face 유의미하게 개선(9~16%p) |
| 완전 해결(100%) | **미달성** — 마진이 정확히 0인 진짜 동률 지점은 이론상 불가능한 한계, 다만 그 지점도 개선은 됐다 |

지금까지 시도한 4가지 방향 중 가장 뚜렷한 개선이라 프로덕션에 반영했다.
