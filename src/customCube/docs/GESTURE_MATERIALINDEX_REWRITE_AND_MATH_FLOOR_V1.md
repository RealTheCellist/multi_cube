# Gesture materialIndex Rewrite + Mathematical Floor v1

## 배경

큐비 외형(베벨 2배, 간격 제거)을 바꾼 뒤 사용자가 "여전히 인식문제는
발생하는구나"라고 리포트했다. 이어서 "스와이프 앤 무브 시스템을 새로
짜보자"는 요청을 받았고, "어느 방향에서 스와이핑을 하든 오류가
발생하지 않는 것으로" 만들어달라는 요구사항이 확인됐다.

## 1단계: 요구사항 자체가 수학적으로 가능한지 먼저 검증

새로 짜기 전에, "스와이프 방향만으로 100% 무오류가 가능한가"부터
순수 기하학으로 직접 계산했다 (레이캐스트 없이, 카메라 투영 수식만).
Top/Front/Right 3개 면 각각에서, 면 전체를 25×25 격자로 촘촘히
스캔하며 두 후보 회전축의 화면상 접선 방향 사이의 실제 각도 차이를
계산했다:

| 면 | 최소 각도 차이 | 15도 미만 비율 | 5도 미만 비율 |
|---|---|---|---|
| Top | **0.03도** | 19.8% | 6.1% |
| Front | **0.07도** | 14.6% | 4.4% |
| Right | **0.19도** | 18.0% | 5.5% |

세 면 모두에서 두 후보 방향이 거의 완전히 겹치는(1도 미만) 지점이
실제로 존재한다. 이 지점들에서는 스와이프 "방향"이라는 정보 자체가
두 선택지를 구분하지 못한다 — 사람 손의 자연스러운 오차(각도 몇 도)로는
0.03도 차이를 구분할 수 없다. **알고리즘을 아무리 잘 짜도, 방향
정보만으로는 이 지점들에서 100% 정확도가 원리적으로 불가능하다.**

이 사실을 사용자에게 그대로 전달했고, 사용자는 UI 힌트를 추가하는 대신
"이 한계를 인정하고 판정 로직만 최대한 다듬자"를 선택했다.

## 2단계: 순수 판정 로직 개선 — materialIndex 기반 축 판정

기존 로직은 터치한 면의 축(faceAxis)을 레이캐스트 히트의 **법선
벡터**에서 가장 큰 성분을 골라 판정했다:

```ts
const worldNormal = hit.face.normal.clone().transformDirection(hit.object.matrixWorld);
const faceAxis = ax >= ay && ax >= az ? "x" : ay >= az ? "y" : "z";
```

법선은 **연속적인 값**이라, 베벨(둥근 모서리) 근처에서는 실제 면
방향에서 점점 벗어난다 — 베벨을 키울수록(이번에 2배로 키웠다) 이
오차가 커질 수 있는 구조였다. 반면 `hit.face.materialIndex`는
`RoundedBoxGeometry`가 `BoxGeometry`를 상속하며 6개 매크로 면 그룹
순서(px,nx,py,ny,pz,nz)를 그대로 유지하기 때문에, 베벨 곡률과
무관하게 **항상 정확한, 이산적인** 값이다 (이미
`INTER_CUBIE_GAP_HIT_FIX_V1.md`의 `isStickerFaceHit`에서 이 사실을
활용한 바 있다).

`customSwipeControls.ts`의 `faceAxis` 판정을 `materialIndex` 기반으로
교체했다 (`CustomCubeScene.axisForMaterialIndex` 신규 추가, 법선 기반은
materialIndex가 없는 예외적 히트에 대한 폴백으로만 유지).

## Validation

**법선 기반 vs materialIndex 기반 실측 대조** (Front/Top/Right면
경계선·모서리 부근, 30개 지점): 두 방법이 선택한 축이 단 한 곳도
불일치하지 않았다 — 이는 이 특정 카메라/기하에서는 원래도 법선 기반이
심각하게 틀리진 않았다는 뜻이지만, materialIndex 기반이 베벨 크기
변화에 구조적으로 더 안전하다는 점은 여전히 유효하다.

**실제 앱에서 수학적 한계 재확인** (Playwright, tremor 스와이프):

1단계에서 찾은 정확한 최악 지점(0.03/0.07/0.19도 차이)에서 N=15씩
실측:

| 지점 | 결과 |
|---|---|
| Top 최악점 (0.03도) | 15/15, 15/15 "오답" — 기준 방향 자체가 두 후보의 이등분선에 거의 걸쳐 있어, "정답"이라는 개념 자체가 불안정한 진짜 축퇴 지점 |
| Front 최악점 (0.07도) | 0/15, 0/15 — 두 후보가 서로 가까워도, 기준 스와이프 방향이 이등분선에서 떨어져 있으면 안정적으로 판정됨 |
| Right 최악점 (0.19도) | 0/15, 0/15 — 동일 |

**핵심 발견**: 두 후보 방향이 가깝다고 해서 항상 불안정한 건 아니다 —
표준 스와이프 기준 방향(가로/세로)이 그 둘의 이등분선에 얼마나
가까운지가 실제 안정성을 결정한다. Top면의 그 한 지점만 우연히
이등분선에 걸쳐 있어 진짜 축퇴(degenerate) 상태였다.

**현실적인 무작위 샘플 종합** (3개 면 × 5지점 무작위, N=10씩, 총
300회): **13/300 오답 (4.3%)** — 1단계에서 계산한 "5도 미만 분리
비율"(4.4~6.1%)과 거의 정확히 일치한다. 순수 기하학 예측이 실제 앱
동작과 실측으로 검증됐다.

**회귀 검사**: `npx tsc --noEmit`, `npm run build` 통과. 2×2/3×3/4×4/5×5
전 사이즈 인터리어 스와이프 정상 동작, 콘솔 에러 0건.

## Decision

**materialIndex 기반 축 판정 적용, 4.3% 잔여 오차율을 확정된
수학적 하한으로 기록.** 이 수치는 버그가 아니라 스와이프 "방향"만으로
3D 회전을 지시하는 인터페이스 자체의 구조적 한계이며, 카메라 각도
최적화(`CAMERA_ANGLE_OPTIMIZATION_VALIDATION_V1.md`)가 이미 줄일 수
있는 만큼 줄인 상태에서 남은 값이다. 추가로 줄이려면 방향 외의 정보
(터치 시점 시각적 힌트, 2단계 확정 방식 등 UI 변경)가 필요하다는 것도
이번 조사로 명확히 확인됐다 — 사용자가 이번 라운드에서는 그 방향을
선택하지 않아 범위 밖으로 남겨둔다.
