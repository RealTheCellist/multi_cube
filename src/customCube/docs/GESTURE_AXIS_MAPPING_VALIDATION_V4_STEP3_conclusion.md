# Gesture 방향 오인식 수정 — 실제 브라우저 검증(STEP3) 결과 보고

## 무엇을 했나

`GESTURE_AXIS_MAPPING_VALIDATION_V4`에서 이미 프로덕션에 반영한 "마진 스케일링
신뢰도 게이트"(`customSwipeControls.ts`)를, 그동안 남아있던 검증 공백 —
헤드리스 수식 시뮬레이션만으로 확인했지 실제 코드 실행으로는 확인하지
않았던 부분 — 을 닫기 위해 실제 브라우저에서 재검증했다.

- `customSwipeControls.ts`에 임시 프로브(`__GESTURE_PROBE_DOWN__`,
  `__GESTURE_PROBE_LOCK__`)를 추가해 실제 프로덕션 코드가 내리는 판정을
  직접 수집.
- 실제 큐비 중심 좌표(마진 스윕으로 찾은 각 면의 최악 지점)에 손떨림 모델
  (스텝당 진폭 4px 노이즈)로 실제 포인터 이벤트를 흘려보냄.
- Right face(마진 0.044), Top face(마진 0.042), Front face(회귀 검사),
  각 N=60/방향(수평·수직), 총 360회 실제 브라우저 상호작용.
- 검증 후 프로브는 전부 되돌렸고(`git diff` 0줄로 확인), 스크래치
  스크립트/심볼릭 링크도 모두 정리함 — 프로덕션 코드에는 STEP3로 인한
  변경이 전혀 없음.

## 실제 수치

| 지점 | STEP1 헤드리스 시뮬레이션 예측 | STEP3 실제 브라우저(N=60/방향) |
|---|---|---|
| Right face 최악(마진 0.044) | 0.0% / 0.0% | **0.0% / 0.0%** — 정확히 일치 |
| Top face 최악(마진 0.042) | 35.3% / 34.7% | **50.0% / 43.3%** — 예측보다 나쁨 |
| Front face(회귀 검사) | 1.3% / 6.7%(불변) | 3.3% / 3.3% — 낮은 수준 유지 |

## 판정

| 기준 | 결과 |
|---|---|
| Front face 회귀 없음 | **통과** — 실제 브라우저에서도 낮은 오인식률(3.3%/3.3%) 유지 |
| Right face 개선 | **통과** — 실제 코드에서도 완전히 해결(0%/0%), 시뮬레이션과 정확히 일치 |
| Top face 개선 | **미달성** — 실제 코드에서는 사실상 동전 던지기 수준(50.0%/43.3%), 시뮬레이션이 예측한 개선폭은 재현되지 않음 |

## 결론

이번 검증으로 두 가지가 갈라졌다:

1. **Right face(면과 면이 뚜렷이 갈리는 지점)의 오인식은 실제로 해결됐다.**
   헤드리스 시뮬레이션 예측과 실제 브라우저 측정치가 정확히 일치(0%/0%) —
   이 부분은 확실한 성과로 볼 수 있다.
2. **Top face 같은 진짜 동률에 가까운 지점(마진 ≈0)은 이 게이트만으로는
   실질적으로 개선되지 않았다.** 시뮬레이션이 예측한 "9~16%p 개선"은 실제
   코드 경로에서 재현되지 않았고, 여전히 거의 50/50 수준이다. 이는
   V4 문서가 이미 밝힌 "마진이 진짜 0에 가까운 지점은 어떤 알고리즘으로도
   이론상 50/50을 벗어날 수 없다"는 기하학적 한계와 부합하는 결과다.

**다음 단계 제안**: 마진 스케일링 게이트는 이미 프로덕션에 반영되어 있고
Right face류 문제는 실제로 고쳤으니 되돌릴 이유는 없다. 다만 Top face류
"진짜 동률" 지점은 게이트 튜닝으로는 넘을 수 없는 기하학적 한계로 보이므로,
이 지점을 더 개선하려면 카메라 각도 자체를 바꾸는 접근(이미 시도했다가
다른 면을 악화시켜 기각한 Yaw 조정과는 다른 조합)이나, 애초에 이 지점에서
발생하는 오동작의 실사용 빈도/영향도를 먼저 측정해 볼 가치가 있는지 확인이
필요하다. 사용자가 원한다면 보류해 둔 모델 연구를 다시 꺼낼 필요는 없다 —
이건 어디까지나 게이트 로직의 한계이지 상태 모델과는 무관한 문제다.
