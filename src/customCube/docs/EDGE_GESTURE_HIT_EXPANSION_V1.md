# Edge Gesture Hit Expansion Sprint v1

**Update (same sprint, continued)**: the original 40px synthetic-swipe
measurement below understated the real fix -- see "Refinement round" at the
end of this document for the corrected, realistic-swipe-distance numbers
and a second, evidence-bounded tuning pass (margin 0.6 → 0.75).

## 배경

사용자 리포트: "3면을 보고 있는 상태에서 우측끝/좌측끝 같이 면과 면 경계쪽에서
스와이프 하면 움직임이 지시대로 움직이지 않았음 (데스크탑에서 확인)".

## Research: 근본원인

Cube Model Lab(`src/modelLab/`)과 실제 프로덕션 게임(`index.html`)에서 동일한
좌표로 동일한 스와이프를 재현해 비교한 결과, 두 페이지가 **완전히 동일하게**
동작함을 확인했다 (`customSwipeControls.ts`를 Model Lab이 전혀 건드리지
않으므로 당연한 결과이지만, 실측으로 재확인). 즉 이 버그는 Model Lab이나
새 큐브 모델 3종과 무관하고, 실제 출시된 게임의 스와이프 판정 로직 자체에
있는 기존 현상이다.

`customSwipeControls.ts`에 임시 계측(EDGE_PROBE, 사용 후 즉시 원복)을 넣어
가장자리 스와이프 5건을 재현한 결과:

- `rightedge_vert_upper/lower`, `leftedge_horiz` (3건): `onPointerDown`의
  레이캐스트가 **아무것도 맞히지 못함** (`EDGE_PROBE pointerdown MISS`).
  터치 좌표가 큐브의 실제 렌더링된 실루엣보다 몇~수십 픽셀 바깥(배경)에
  떨어진 경우다.
- `leftedge_vert` (1건): 레이캐스트는 성공했지만, 그 지점에서 두 후보 축(x/y)의
  화면상 접선(tangent) 정렬도가 `align0=0.943` vs `align1=0.9996`로 거의
  동률(diff=0.056)이었다 — `LOW_CONFIDENCE_MARGIN` 로직이 이미 처리하려는
  바로 그 근본 원인(오블리크 각도에서 두 후보 축의 접선이 거의 평행해지는
  현상)이 큐브의 실루엣 경계에서 극단적으로 심해진 사례.

첫 번째 원인(레이캐스트 자체가 miss)이 정량적으로 훨씬 큰 비중을 차지했다.

## Blueprint

- **전략 A (채택)**: 실제 큐비 메쉬들을 감싸는, 조금 더 큰 투명 히트박스
  프록시를 추가하고, 기존 레이캐스트가 완전히 실패했을 때만 그 프록시를
  2차로 시도한다. 인터리어 제스처의 판정 로직은 전혀 건드리지 않으므로
  회귀 위험이 구조적으로 0에 가깝다.
- **전략 B (보류)**: `LOW_CONFIDENCE_MARGIN`/`LOW_CONFIDENCE_EXTRA_PX`를
  더 완화. 근거 데이터가 이번 라운드에서 1건뿐이고, 이미 별도
  CameraExpansion 스프린트가 같은 종류의 모호성을 조사해 "카메라 각도로는
  구조적으로 해결 불가(Decision B)"라는 결론을 낸 바 있어, 약한 근거로
  이미 튜닝된 임계값을 건드리는 것은 회귀 위험 대비 효용이 낮다고 판단해
  이번 라운드에서는 보류.

## Prototype (구현)

- `CustomCubeScene.ts`: 큐브의 실제 렌더링 표면(`trueHalfExtent`)보다
  `spacing * 0.6`만큼 더 큰 투명(`opacity: 0`) 박스(`edgeGestureProxy`)를
  추가. `raycastableObjects()`(1차 판정용)에는 포함시키지 않고, 별도
  `edgeGestureProxyObjects()`로만 노출 — 기존 판정 경로는 코드 경로 수준에서
  전혀 변경되지 않는다.
- `customSwipeControls.ts`: `raycastNear`가 기존 9칸 재시도 링에서도
  실패하면, 정확히 그 지점 한 번만 프록시에 대해 재시도한다. 그리고
  `onPointerDown`에서 "실제 큐비여야 한다"는 기존 존재 검사를 제거했다
  (원래도 그 변수는 존재 여부 확인에만 쓰였고 이후 로직에서 전혀
  참조되지 않았음 — 죽은 코드였다). 프록시 히트는 실제 표면보다 바깥에서
  일어나므로, 레이어 후보 계산 결과를 그리드의 가장 바깥 레이어로
  clamp해서 존재하지 않는 레이어(빈 턴 그룹)를 만들지 않게 했다.

## Validation

**핵심 지표 (측정, N=112, 좌우 가장자리 8개 x축 위치 x 7개 높이 x
가로/세로 2방향, 3x3x3)**:

| | 수정 전 | 수정 후 |
|---|---|---|
| 가장자리 스와이프 성공률 | 8.9% (10/112) | 44.6% (50/112) |

수정 전 `git stash`로 원본 코드를 복구해 동일 스윕을 먼저 측정한 뒤,
`stash pop`으로 복구해 재측정 — 우연이 아니라 이 변경이 만든 차이임을
직접 대조로 확인했다.

**회귀 검사**: 인터리어(정면/윗면/오른쪽면 안쪽) 스와이프 4종을 수정 전/후
스크린샷으로 비교 — 픽셀 단위로 동일. 프로덕션과 Model Lab(3개 모델 전부)도
계속 서로 일치.

**그리드 크기 회귀**: 2x2/4x4/5x5 각각 인터리어 스와이프 스모크 테스트 —
전부 정상 커밋, 콘솔 에러 0건.

**남은 miss(62/112, 55.4%)의 성격**: 대부분 `fx=0.94~0.98`(큐브 실루엣에서
더 멀리 떨어진, 명백히 배경인 지점)에 몰려 있다 — 프록시 마진을 더 키우면
줄일 수 있지만, 그만큼 "명백히 큐브 바깥을 만졌는데도 반응하는" 다른 종류의
오작동을 만들 위험이 커진다. 이번 라운드는 "큐브 표면을 스와이프했는데
아무 반응이 없다"는 리포트된 증상을 줄이는 것을 목표로, 보수적인 마진
(`spacing * 0.6`)을 선택했다.

## Decision (1차)

**A: 적용** — 회귀 없이 가장자리 스와이프 성공률을 8.9% → 44.6%로 개선했다.
`customSwipeControls.ts`/`CustomCubeScene.ts` 양쪽 다 인터리어 판정 경로는
1바이트도 바뀌지 않았고(fallback 전용 추가), 실측으로 이를 확인했다.

남은 미해결 영역(더 먼 배경 지점, 그리고 진짜 근접-동률 축 모호성)은 각각
"의도적으로 반응하지 않아야 하는 영역"과 "카메라 각도 스프린트가 이미
구조적 한계로 결론 낸 영역"에 가까워, 이번 스프린트 범위 밖으로 남겨둔다.

## Refinement round (같은 스프린트, 계속)

사용자가 "이 문제 해결을 위한 스프린트를 진행하자"고 요청해 계속 조사했다.

### 재측정 — 원래 40px 테스트 스와이프가 결과를 과소평가했음을 발견

위 8.9% → 44.6% 수치는 합성 스와이프 거리를 40px로 고정해서 측정한 것이다.
그런데 이 카메라/캔버스 크기에서 커밋에 필요한 실효 드래그 거리는 40px보다
훨씬 크다 — 특히 `LOW_CONFIDENCE_EXTRA_PX`가 발동하는 지점은 락(lock)
자체가 늦게 걸려서 40px로는 커밋 문턱(0.3)을 넘기지도 못하는 경우가 많았다.

동일한 112개 지점을 80px 스와이프로 재측정(수정 전/후 모두 `git checkout
HEAD~1`로 되돌려 대조):

| | 40px 스와이프 (최초 측정) | 80px 스와이프 (현실적 거리, 재측정) |
|---|---|---|
| 수정 전 | 8.9% (10/112) | 30.4% (34/112) |
| 수정 후 (margin 0.6) | 44.6% (50/112) | 92.0% (103/112, 재현성 확인용 2회 측정 91.1%/92.0%) |

즉 실제 개선폭은 최초 보고했던 것보다 훨씬 크다 (30.4% → 92.0%).

### 잔여 실패(8%) 원인 분류

남은 9개 실패 지점에 임시 계측을 넣어 원인을 정확히 나눴다:
- **6/9**: 프록시로도 여전히 못 맞히는, 캔버스 최극단 모서리(fx 0.94~0.98,
  fy 0.72~0.82) — 마진을 더 키우면 해결 가능한 부류.
- **3/9**: 락은 걸렸지만 `align0`/`align1`이 둘 다 매우 낮아(0.02~0.21,
  즉 스와이프 방향이 두 후보 축 접선 모두와 거의 수직) 80px를 다 써도
  커밋 문턱(0.3)을 못 넘김 — 이 지점 자체가 기하학적으로 약한 신호이므로
  "더 기다리기"로는 해결이 안 되는 부류. LOW_CONFIDENCE 로직은 이미 최대한
  기다리고 있다.

### 마진 확장 실험 — 안전한 상한 확인

첫 번째 부류(프록시 미스)를 줄이려고 `EDGE_MARGIN_RATIO`를 올려봤다:

| margin | 112개 가장자리 히트율 | 배경 7개 지점 오탐(false positive)율 |
|---|---|---|
| 0.6 (최초 커밋) | 92.0% | 1/7 (캔버스 최상단 중앙 1곳 — 큐브 윗면 꼭짓점과 가까워 정당할 가능성) |
| 0.75 | 94.6% | 1/7 (0.6과 동일) |
| 0.8 | 측정 안 함 | 2/7 |
| 0.9 | 측정 안 함 | 5/7 |
| 1.5 | 98.2% | **7/7 (전부 오탐 — 캔버스 배경 아무 데나 스와이프해도 큐브가 돌아감)** |

1.5는 완전히 못 쓸 수준(배경 터치가 전부 오작동으로 이어짐)이었고, 0.8부터
이미 오탐이 늘기 시작했다. **0.75**는 0.6과 똑같은 오탐 프로필(1/7, 이미
용인된 지점)을 유지하면서 히트율만 92.0% → 94.6%로 올렸다 — 이 값을
최종값으로 채택.

### 최종 검증 (margin 0.75)

- 112개 가장자리 스와이프: **94.6%** (106/112)
- 배경 오탐 7개 지점: 1/7 (0.6과 동일, 회귀 없음)
- 인터리어 스와이프 4종 + 그리드 크기 2×2/4×4/5×5: 회귀 없음 (스크린샷
  픽셀 단위 동일, 콘솔 에러 0건)
- `npx tsc --noEmit`, `npm run build`: 통과

## Decision (최종)

**margin 0.75로 확정, 커밋.** 남은 5.4%는 (a) 마진을 더 키우면 오탐이
기하급수적으로 늘어나는 걸 실측으로 확인한 "닿지 않는 게 맞는" 영역과,
(b) 스와이프 방향이 두 후보 축 모두와 기하학적으로 거의 수직이라 "더
기다리기"로 해결 안 되는, CameraExpansion 스프린트가 이미 구조적 한계로
결론 낸 것과 같은 종류의 근본적 모호 지점이 대부분이다. 추가 개선은 다른
카메라 각도나 다른 판정 알고리즘(예: 두 손가락 힌트, 스냅 존)이 필요한,
이번 스프린트 범위를 넘는 작업으로 판단한다.
