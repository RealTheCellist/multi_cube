# Gesture Axis Mapping — Late Correction v1

## 배경

`GESTURE_AXIS_MAPPING_VALIDATION_V4`의 STEP3 실제 브라우저 검증에서, 마진
스케일링 신뢰도 게이트가 Right face(면 경계가 뚜렷한 지점, 마진 0.044)는
완전히 해결했지만(0%/0%), Top face 같은 진짜 동률에 가까운 지점(마진
0.042)은 여전히 개선 폭이 작다는(50.0%/43.3%, 시뮬레이션이 예측한
35.3%/34.7%에도 못 미침) 정직한 한계가 드러났다. 사용자가 "좀더
개선해보자"고 요청해, 다섯 번째 방향을 탐색했다.

## 왜 "더 기다리기"는 한계가 있는가

기존 게이트(V3, V4)는 전부 "잠그기 전에 얼마나 기다릴지"만 조절한다. 하지만
마진이 진짜 0에 가까운 지점에서는, 오래 기다려도 누적 드래그 벡터의
**각도 노이즈**가 줄어들 뿐 — 마진 자체가 그 노이즈보다 작으면, 아무리
기다려도 판정이 근본적으로 동전 던지기에 가깝다. 반대로 말하면, 손 떨림
노이즈는 이동 거리가 늘수록(무작위 보행이라) 상대적으로 줄어들긴 하지만,
마진이 그보다 훨씬 작으면 실질적 개선 속도가 매우 느리다 — 유효 드래그
거리(약 110px)로는 부족하다.

## 아이디어 — 잠근 후에도 계속 지켜보기

기존 로직은 축이 한 번 잠기면(`drag.locked` 설정) 그 이후로는 두 후보를
다시 비교하지 않는다. 하지만 게이트를 통과해 잠긴 순간의 스냅샷이 여전히
저신뢰 상태였다면, 그 이후 드래그가 계속되면서 누적 방향 벡터에 더 많은
실제 신호가 쌓인다 — 이걸 버리지 않고 계속 활용하면 어떨까?

`onPointerMove`에 게이트를 하나 더 추가했다: 잠긴 이후에도(단 한 번만)
동일한 `settleRef` 기준 누적 방향으로 두 후보를 계속 비교하다가, 반대
후보가 `CORRECTION_MARGIN`(= 기존 `LOW_CONFIDENCE_MARGIN`, 0.15) 이상
확신 있게 앞서면 축을 교체한다. 이미 커밋된 무브는 없으므로(라이브
스크럽 중), `scene.endTurn(null)`로 되돌리고 `scene.beginTurn()`으로 새
축을 다시 시작 — 이미 초기 잠금이 쓰는 것과 같은 catch-up 트윈으로
부드럽게 전환된다.

잘 분리된 면(Front face 등)은 마진이 항상 0.15보다 훨씬 크므로, 반대
후보가 "확신 있게 앞서는" 일이 애초에 일어나지 않는다 — 즉 이 로직은
기존에 이미 잘 동작하던 케이스를 건드릴 수 없는 구조다.

## 검증 STEP1 — 헤드리스 시뮬레이션 + 임계값 스윕

`customSwipeControls.ts`의 수식을 그대로 복제한 독립 스크립트로, 기존
게이트만 있는 baseline과 late-correction을 추가한 candidate를 같은 손떨림
경로(N=300/방향)로 페어 비교했다. `CORRECTION_MARGIN`을 0.10~0.35로
스윕해 정확도 개선폭과 "flip"(축 교체) 빈도 사이의 트레이드오프를 확인:

| 지점 | 임계값 | 오인식률 | flip 비율 |
|---|---|---|---|
| Top face (마진 0.042) | 0.10 | 34.7~37.3% | 111~135/300 |
| Top face | **0.15 (채택)** | 38.3~40.7% | 73~96/300 |
| Top face | 0.35 | 41.0~46.3% (baseline과 거의 동일) | 10~22/300 |
| Front face(회귀 검사) | 0.15 | 0.0~0.3% (baseline 4.0~6.0%에서 개선) | 12~18/300, broke 0~1 |
| Right face(마진 0.044) | 전체 | 0.0% (불변) | 0 |

`LOW_CONFIDENCE_MARGIN`과 같은 0.15를 택했다 — 새로운 매직 넘버를
추가하지 않고 "확신"이라는 개념을 파일 전체에서 하나로 유지하기 위해서다.
이 지점에서 Right face는 전혀 영향받지 않고, Front face는 오히려
개선되며(초기 잠금의 우연한 노이즈를 뒤이은 실제 데이터로 정정), Top
face는 유의미하게(약 5~8%p) 개선됐다.

## 검증 STEP2 — 실제 코드 통합/기능 검증 (Playwright, 실제 dev 빌드)

- 실제 dev 서버에서 3x3 큐브를 선택한 뒤, 정면 수평/수직 스와이프 2회 +
  Top/Right 경계 부근(교정이 자주 발동할 것으로 예상되는 오블리크 각)
  스와이프 10회, 총 12회 실행: 이동수 카운터가 정확히 12로 증가, 크래시나
  멈춤 없음. `endTurn(null)` → `beginTurn()` 되돌리기-재시작 시퀀스가 실제
  씬에서도 안전하게 동작함을 확인.
- 콘솔/페이지 에러 0건(샌드박스 네트워크 제약으로 인한 기존 리소스 로드
  실패 1건은 무관함을 별도 확인).

## 검증 STEP3 — 실제 코드 경로 통계 재검증 (Playwright, 실제 브라우저)

`GESTURE_AXIS_MAPPING_VALIDATION_V4` STEP3와 동일한 방법론(임시 프로브,
실제 큐비 중심 좌표, N=60/방향)으로 이번 late-correction 추가분을 재검증.
프로브는 매 잠금(초기 잠금 + 교정)마다 기록하고, 제스처당 **마지막**
기록을 최종 판정으로 채택했다. 검증 후 프로브는 전부 되돌렸다(`git diff`
0줄 확인).

| 지점 | STEP3(V4, 교정 없음) | 이번(late correction 포함) |
|---|---|---|
| Right face(마진 0.044) | 0.0% / 0.0% | **0.0% / 0.0%** — 불변, 여전히 완전 해결 |
| Top face(마진 0.042) | 50.0% / 43.3% | **41.7% / 33.3%** — 8.3%p / 10.0%p 개선 |
| Front face(회귀 검사) | 3.3% / 3.3% | **0.0% / 0.0%** — 오히려 개선(회귀 없음) |

교정 발동 비율: Top face 28.3%/36.7%(예상대로 저마진 지점에서 자주
발동), Front face 3.3%/3.3%(예상대로 거의 발동 안 함), Right face 0%.
헤드리스 시뮬레이션의 임계값 0.15 예측(Top face 38.3~40.7%, Front face
0.0~0.3%)과 실제 측정치(Top face 33.3~41.7%, Front face 0.0%)가 같은
방향·비슷한 크기로 일치한다.

## 판정

| 기준 | 결과 |
|---|---|
| Front face 회귀 없음 | **통과** — 오히려 개선(3.3%/3.3% → 0.0%/0.0%), 실제 브라우저 통계로 확인 |
| Right face 유지 | **통과** — 완전히 불변(0%/0%), flip 자체가 발생하지 않음 |
| Top face 추가 개선 | **통과** — 실제 브라우저에서 8.3~10.0%p 추가 개선 확인 |
| 완전 해결(100%) | **미달성** — 여전히 마진이 0에 가까운 진짜 동률은 이론적 한계, 다만 V4 단독보다는 명확히 나아짐 |

이번 추가로 지금까지 시도한 5가지 방향 중 가장 뚜렷한 실측 개선이라
프로덕션에 반영했다. Top face류 지점의 남은 오인식은 여전히 순수 각도
비교의 근본적 한계(기하학적 동률)이며, 이 이상의 개선은 카메라 각도
변경이나 다른 신호(터치 압력, 속도 등)를 필요로 할 가능성이 크다.
